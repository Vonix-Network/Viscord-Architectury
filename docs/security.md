# Security Model

Viscord stores secrets and handles cross-platform identity. This page enumerates the security-relevant behavior that the implementation actually provides, so you can decide where to add defense in depth on your side.

## Secrets at rest

| Secret | Location | Notes |
|---|---|---|
| Discord bot token | `config/viscord/viscord.toml` → `discord.bot_token` | Plaintext TOML. File permissions are your responsibility — `chmod 600` and a non-world-readable directory are recommended. |
| Discord webhook URL (contains a token segment) | `config/viscord/viscord.toml` → `discord.webhook_url` | Same as above. The token is the random-looking string at the end of the URL. |
| Fluxer bot token | `config/viscord/viscord.toml` → `fluxer.bot_token` | Same. |
| Fluxer webhook URL | `config/viscord/viscord.toml` → `fluxer.webhook_url` | Same. |
| Linked accounts | `config/viscord/linked_accounts.json` | Flat JSON map of MC UUIDs → Discord IDs. No secrets, but identifying. |

Viscord does **not** read environment variables for tokens, and does not load a separate `.env`. If you want to keep tokens out of `viscord.toml`, the supported pattern today is to keep `viscord.toml` itself out of source control / in an encrypted volume.

## Log redaction

`WebhookClient` and `FluxerWebhookClient` previously included full webhook URLs (including the bearer token segment) in error/warn log lines on send failure or URL-parse failure — every time a webhook send misbehaved, the token went to disk.

Since **4.2.0**, both clients route every URL through `redactWebhookUrl()` which emits `…/webhooks/{id}/***`. The webhook ID is still logged (useful for diagnostics) but the token segment is gone.

Bot tokens are **not** logged by Viscord anywhere — they're held in memory in `BotClient.api` / `FluxerBotClient.token` and passed to the Javacord / Fluxer client without ever being printed.

## Account linking

The 6-digit link-code flow has several hardening properties; see [account-linking.md](account-linking.md) for the full table. Highlights:

- Codes are generated by a shared `SecureRandom` instance, not `new Random()` (4.1.7).
- The "is this Discord already linked?" check and the `linkedAccounts.put()` are bracketed in `synchronized (linkedAccounts)` so concurrent `/link` calls cannot bind one Discord ID to two MC UUIDs (4.1.7).
- Codes expire after `account_linking.code_expiry` seconds (60–600, default 300).
- The link-code map is in-memory only — codes do not survive a server restart.

## Filter integrity

The cross-server bot/webhook allowlist (`filters.trusted_bot_ids`) is the only mechanism that lets external bots send embeds into your in-game chat. By default `filters.ignore_bots = true` and `filters.ignore_webhooks = true`, so the path is closed until you explicitly open it. Add only the IDs of bots you operate or trust.

When designing a multi-server setup that uses `trusted_bot_ids`, remember that **any** message from a trusted bot will pass the bot/webhook filter — embed detection is the next layer. Treat the allowlist as a "this bot is a peer Viscord instance, not a content-source allowlist".

## Webhook tokens — operational notes

- Webhook URLs grant **send-as-anyone-in-this-channel** capability. If a webhook URL leaks, rotate it (Discord channel settings → Integrations → Webhooks → delete & recreate).
- `discord.webhook_id` is auto-extracted from `discord.webhook_url`; you only need to set it manually if you want explicit override.
- Rotating a webhook does **not** require restart — edit `viscord.toml` and run `/viscord reload`.

## Bot permissions

Give the Discord bot only what it needs in the bridged channel:

- View Channel
- Send Messages
- Read Message History
- Embed Links
- (Optional) Manage Webhooks — only required if you want Viscord to introspect / auto-extract webhook IDs in some flows.

Avoid giving the bot guild-wide admin or `MENTION_EVERYONE` unless you have a specific reason.

## Privacy

- Discord display names are resolved as `server nickname → global display name → username` by default (`messages.use_display_name = true`). Set to `false` to use plain `@username` only — useful in privacy-sensitive deployments.
- The `MENTION_EVERYONE` payload is handled at Discord's side, not Viscord's — Viscord does not strip or escape `@everyone`/`@here` from MC → Discord. If you want to prevent players from triggering mass mentions, deny `MENTION_EVERYONE` on the webhook's channel at Discord's permission layer.

## TLS & integrity

- All Discord / Fluxer HTTP traffic goes through OkHttp with the JVM's default truststore.
- Linked accounts I/O explicitly uses `StandardCharsets.UTF_8` (4.1.7) to prevent non-ASCII corruption on platforms where the default charset isn't UTF-8 (mainly Windows).

## What Viscord does **not** do

- It does not enforce any role-mapping between Discord roles and Minecraft permissions.
- It does not sign or HMAC its webhook payloads (it relies on Discord's URL-token model).
- It does not encrypt `viscord.toml` at rest.
- It does not audit-log player actions to Discord on its own — only the event categories you enable in `[messages.events]`.

If you need any of those, layer them on top with another mod / platform integration.
